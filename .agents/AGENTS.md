# Custom behavioral rules for Antigravity AI agent in this project

- **Правило по триггеру №1 (Приветствие)**: Кассир НЕ обязан представляться по имени. Обязательным является только вежливое приветствие («Добрый день/утро/вечер!», «Добро пожаловать!»). Использование сухого слова «Здравствуйте» разрешено, но стоп-слово «Здрасьте» или «Здрасти» является нарушением лояльности (автоштраф).

- **Правило по коммитам и деплою (Строгий запрет)**: Агенту ЗАПРЕЩЕНО выполнять любые команды коммита и отправки кода в репозитории (`git commit`, `git push`, копирование и деплой) без предварительного явного согласия и текстового разрешения пользователя в чате. Любые правки файлов должны оставаться локальными до получения подтверждения на отправку.

- **Правило Git Flow (Начало работы)**: Каждый раз, когда мы начинаем корректировать этот проект, агент ОБЯЗАН первым делом спросить у пользователя: **«В какой ветке мы сегодня работаем?»**. 
  Агент должен дождаться ответа, проверить текущую ветку через `git status` и при необходимости переключиться на указанную пользователем ветку (или создать её). Только после этого можно приступать к написанию или изменению кода. Строго различать задачи для продакшена (бэкенд/основа) и задачи для лендинга/демо (GitHub/Vercel).


- **Запрет на самостоятельный коммит**: Агенту строго запрещается делать git commit и git push без явного разрешения пользователя, даже если ранее в диалоге такое разрешение давалось. Разрешение должно быть получено на каждый конкретный коммит.

- **Правило по работе с клиентами (Target Cabinet)**: При постановке задачи на изменение логики или UI, агент обязан уточнить "Целевой кабинет" (Target Cabinet). 
  - Если задача касается всех (например, багфикс ядра), изменения вносятся в общий код.
  - Если задача специфична для клиента (например, скрипты продаж для IBSPharm), агент не должен писать хардкод в файлы, а должен изменять настройки клиента (system_prompt, checklist_items, kpi_config) в Базе Данных.
  - Если клиенту нужен уникальный UI/UX элемент, агент вносит изменения в мастер-ветку с использованием Feature Flags (например, `if (org_slug === 'ibs_pharm_v2')`).

- **Правило по песочнице (BypassSandbox)**: Любые команды, требующие выхода в интернет (`git push`, `git fetch`, `ssh`, `scp` на VPS, curl к внешним API), ДОЛЖНЫ выполняться с параметром `BypassSandbox: true`. Стандартная песочница блокирует сеть, что приводит к ложным ошибкам доступа (например, 403 от GitHub или Connection refused). Агент не должен сообщать пользователю об ошибке доступа, пока не проверит выполнение команды вне песочницы.

- **Правило по VPS/Продакшену (Строгий запрет)**: Агенту **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** выполнять любые деструктивные или модифицирующие операции на VPS-сервере и в продакшен-окружении без предварительного представления плана и получения команды **ПРИСТУПАЙ**. К таким операциям относятся:
  - Перемещение, удаление, переименование файлов и папок в S3/MinIO хранилище
  - Остановка, перезапуск, пересоздание Docker-контейнеров (`docker stop`, `docker restart`, `docker compose up -d`, `docker rm`)
  - Любые INSERT/UPDATE/DELETE запросы к базе данных PostgreSQL
  - Изменение `.env` файлов и конфигураций на сервере
  - Запуск скриптов, изменяющих данные (`python3 /tmp/move*.py` и т.п.)
  - **Разрешено БЕЗ согласования** (только чтение): `docker logs`, `docker ps`, SQL `SELECT`, `ls`, `cat`, `grep`, `find`, S3 `list_objects`

- **Правило по бэкапам (Обязательная проверка)**: Перед выполнением ЛЮБОЙ операции, которая может привести к потере данных (перемещение файлов, изменение маршрутизации, обновление БД), агент ОБЯЗАН:
  1. Спросить у пользователя о наличии актуального бэкапа
  2. Убедиться, что бэкап существует и доступен
  3. Предложить план отката (rollback plan) в случае неудачи
  4. Только после подтверждения пользователя приступать к изменениям

- **Правило антикаскада (Стоп-правило)**: Если агент допустил ошибку при выполнении операции, ему **ЗАПРЕЩЕНО** пытаться самостоятельно исправить последствия новыми операциями. Вместо этого агент ОБЯЗАН:
  1. Немедленно остановиться
  2. Честно доложить пользователю что именно сломалось
  3. Представить план восстановления
  4. Дождаться команды **ПРИСТУПАЙ** перед любыми корректирующими действиями

- **Правило сохранения статуса анализа (Первоочередная задача)**: При выполнении ЛЮБЫХ правок в проекте (особенно связанных с БД, скриптами пайплайна, обработкой MinIO или перекладыванием файлов) агенту **СТРОГО ЗАПРЕЩЕНО** удалять, сбрасывать на 'new' или терять текущий статус уже проанализированных диалогов. Повторный запуск платного API (Gemini) для уже обработанных файлов недопустим, так как это ведет к двойным расходам. Сохранность данных, уже готовых транскрипций и статусов анализа — абсолютный приоритет при любых изменениях.
